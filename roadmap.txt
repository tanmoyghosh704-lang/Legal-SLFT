================================================================================
PROJECT ROADMAP & RESOURCE BREAKDOWN: LEGAL SLM ALIGNMENT VIA SFT & DPO
(AS ACTUALLY BUILT -- Qwen2.5-3B-Instruct on CUAD)
================================================================================

PROJECT OVERVIEW:
Fine-tuning and aligning Qwen/Qwen2.5-3B-Instruct for grounded IRAC (Issue,
Rule, Application, Conclusion) legal analysis of contract clauses, using
Supervised Fine-Tuning (SFT/QLoRA) and Direct Preference Optimization (DPO),
with a 5-run ablation grid and dual-metric evaluation (deterministic rubric +
LLM-as-judge) to measure exactly how much each alignment stage helps.

This file documents the real workflow used, not a generic plan -- every phase
below names the actual script, dataset revision, config value, and bug that
was hit. Full blow-by-blow reasoning: LOG.md. Distilled results write-up:
WRITEUP.md.

================================================================================
PHASE 1: ACCOUNTS, COMPUTE & ENVIRONMENT SETUP
================================================================================

1. ACCOUNTS & ACCESS KEYS USED:
   - Hugging Face account (model/dataset download, no gated license needed --
     Qwen2.5-3B-Instruct is openly licensed, unlike Gemma/Llama).
   - Kaggle account with GPU quota (T4 x2 sessions, ~9-12h session cap).
   - Ollama running locally AND on Kaggle (teacher generation + LLM judge both
     go through Ollama, not a paid API -- no OpenAI/Anthropic key needed).

2. HARD COMPUTE CONSTRAINT THAT SHAPED THE WHOLE PROJECT:
   - Local hardware: 4GB GTX 1650. Cannot fit even 4-bit inference of a 3B
     model reliably, and training was never viable locally.
   - Rule followed throughout: all heavy compute (teacher generation,
     training, full-dataset judging) runs on free Kaggle GPU time. Local
     machine is for smoke tests (0.5B model), unit tests, and -- once
     weights are trained -- final serving only.

3. SOFTWARE ACTUALLY INSTALLED (requirements.txt, phased):
   - Data prep / local dev (installed first):
     pyyaml, requests, pandas, datasets, huggingface_hub, tqdm, jsonlines,
     scikit-learn
   - Training (mirrored on Kaggle; only pulled in locally for the 0.5B smoke
     test, and later for serving -- see Phase 6's environment bug):
     torch==2.5.1 (pinned -- see note below), transformers, trl, peft,
     bitsandbytes, accelerate, mlflow
   - Eval: ollama (Python client)
   - Serving: fastapi, uvicorn
   - Versioning: dvc
   - Testing: pytest

   IMPORTANT LESSON (hit for real, not hypothetical): torch was originally
   left unpinned. Installing accelerate/bitsandbytes locally for the FastAPI
   phase silently upgraded torch to a CPU-only 2.11.0 wheel, killing CUDA and
   cascading into broken transformers/peft imports. Fixed by pinning
   torch==2.5.1 and reinstalling against the CUDA 12.1 index:
     pip install torch==2.5.1 --index-url https://download.pytorch.org/whl/cu121
   Lesson: after ANY pip install in a GPU project, re-verify
   torch.cuda.is_available() before trusting anything else.

4. KAGGLE-SPECIFIC ENVIRONMENT FIXES REQUIRED (see Phase 4 for the full
   debugging chain):
   - Always pin device_map={"":0} explicitly -- a bare model-id string or
     device_map="auto" on a Kaggle "T4x2" session silently splits the model
     pipeline-parallel across both GPUs, which does not fail, just runs
     10-40x slower with no error.
   - T4/Turing GPUs (compute capability 7.5) do NOT have Tensor Core bf16
     acceleration -- only Ampere+ (8.0+) does. bf16=True on a T4 silently
     runs unaccelerated rather than erroring. Compute GPU capability at
     runtime and fall back to fp16 on pre-Ampere hardware.
   - gradient_checkpointing must be explicitly enabled for 3B-scale training
     on a single T4 or it OOMs (invisible at 0.5B smoke-test scale).

================================================================================
PHASE 2: BASE MODEL
================================================================================

1. MODEL: Qwen/Qwen2.5-3B-Instruct (openly licensed, no approval wait).
   - config.yaml keeps a model.candidates map with a 0.5B variant for local
     smoke tests and the 3B variant (model.active) for real runs -- never
     hardcode the model id inline in a script.

2. HOW IT'S ACTUALLY LOADED (src/eval/generate.py, src/serving/app.py,
   src/train/train_sft.py / train_dpo.py -- one shared pattern):

   from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

   quantization_config = BitsAndBytesConfig(
       load_in_4bit=True,
       bnb_4bit_quant_type="nf4",
       bnb_4bit_compute_dtype=torch.bfloat16,   # or fp16 on pre-Ampere, see Phase 1
   )
   model = AutoModelForCausalLM.from_pretrained(
       model_id,
       quantization_config=quantization_config,
       device_map={"": 0},                       # single-GPU pin -- see Phase 1
       dtype=torch.bfloat16,
   )

   Note: 4-bit quantization happens AFTER download and AT LOAD TIME. The
   downloaded .safetensors files are still full bf16 size (~6GB for 3B
   params) regardless of load_in_4bit -- there is no smaller pre-quantized
   download shortcut for a stock HF model id.

================================================================================
PHASE 3: SFT DATA -- BUILT FROM CUAD, NOT HAND-WRITTEN
================================================================================

1. SOURCE DATASET: CUAD (Contract Understanding Atticus Dataset)
   - Loaded via theatticusproject/cuad-qa at
     revision="refs/convert/parquet" -- the auto-generated Parquet export.
     REQUIRED because HF deprecated script-based dataset loading in
     `datasets` 5.0.1, breaking the originally-planned loading path.
   - 22,450 raw rows, 408 unique contracts, 41 clause categories.
   - Excluded 5 purely-administrative categories (Parties, Document Name,
     Agreement Date, Effective Date, Expiration Date) -- these are pure
     extraction tasks with no legal "Issue" to raise; forcing IRAC onto
     them would just teach vacuous, templated output.
   - Input unit is the extracted CLAUSE SPAN (median ~31 words), not the
     full contract (avg ~8,800 words, up to ~27,000) -- a deliberate scope
     decision, analysis quality per clause is what's being measured, not
     retrieval from a full document.
   - Result: 7,620 (category, clause) rows queued across 36 categories.

2. TEACHER GENERATION (src/data/generate_teacher_targets.py):
   - Model: qwen2.5:7b-instruct-q4_0, served via OLLAMA on Kaggle -- NOT
     raw `transformers` batched generation. This was a pivot forced by 4
     separate bugs in the raw-transformers path (see Phase 4, step 1):
     right-padding corrupting the KV cache, device_map="auto" splitting
     the model across GPUs, unbounded max_new_tokens letting one rambling
     response hold a whole batch hostage, and bf16 weights alone leaving
     no memory headroom on a single T4. Ollama's own scheduler absorbed
     all four problems at once -- the single highest-leverage
     infrastructure decision in the project.
   - Output format (one canonical prompt template, src/data/build_irac.py's
     CANONICAL_PROMPT_TEMPLATE -- imported everywhere, never redefined
     inline, per this project's own rule):

     {"id": ..., "category": "Non-Compete", "clause_text": "...",
      "prompt": "<CANONICAL_PROMPT_TEMPLATE.format(category=..., clause_text=...)>",
      "target": "Issue: ...\nRule: ...\nApplication: ...\nConclusion: ..."}

   - Result: 7,620/7,620 rows generated, 100% parse_ok, 0 duplicate ids,
     all 36 categories and 384 contracts represented.

3. CLEANING (src/data/clean_sft.py):
   - Manual review of a 60-row stratified sample (25 lowest-rubric-scoring
     + 35 random) surfaced 5 real data-quality issues (fragments,
     self-contradictions, a fabricated legal principle, role-swap
     duplicates, unsupported gloss) -- see WRITEUP.md Section 5 for detail.
   - is_substantive_clause() filters unusable CUAD extraction fragments
     (e.g. a "clause" that's just the word "This").
   - find_duplicate_documents() detects the same filing uploaded twice
     under different contract-title strings (2 confirmed real cases) and
     merges BEFORE split assignment, so a duplicate can't leak across
     train/test under a different name. Deliberately conservative
     (requires >=3 shared identical clauses AND matching normalized
     company-name prefix).
   - Final: 7,516 rows (11 confirmed-bad + 93 fragments removed).

4. SPLITTING (src/data/split.py):
   - CONTRACT-LEVEL splits, never clause-level -- a clause from one
     contract must never appear in both train and test.
   - Result: 5,987 / 726 / 803 rows -> train/valid/test, across
     307/38/39 contracts.

================================================================================
PHASE 4: DPO DATA -- PROGRAMMATIC CORRUPTION, NOT A SECOND TEACHER CALL
================================================================================

1. PURPOSE: reduce hallucination/ungroundedness and reinforce IRAC
   structure via explicit contrastive (chosen vs. rejected) signal, on top
   of what SFT alone teaches.

2. GENERATION METHOD (src/data/corrupt.py + src/data/build_dpo.py):
   - chosen = the same clean teacher target used for SFT.
   - rejected = that same target run through ONE of six PROGRAMMATIC
     corruption types: drop a section, reorder sections, insert a
     fabricated citation, insert an unsupported claim, contradict the
     conclusion, truncate.
   - Corruption type is seeded deterministically per row id via
     hashlib.sha256 -- NOT Python's builtin hash(), which is randomized
     per-process unless PYTHONHASHSEED is fixed (this would have made
     corruption type silently non-reproducible across runs; caught before
     it shipped).
   - Explicit, stated-plainly limitation: these are mechanical corruptions
     of already-correct answers, not real human preference judgments --
     narrower than genuine RLHF preference data.

3. RESULT: 7,516 pairs, one per cleaned SFT row. Same contract-level split
   applied identically to DPO pairs -- verified directly (not assumed) that
   SFT and DPO splits agree exactly on which row ids land in train/valid/test.

   {"id": ..., "prompt": "<same CANONICAL_PROMPT_TEMPLATE rendering>",
    "chosen": "Issue: ...\nRule: ...\nApplication: ...\nConclusion: ...",
    "rejected": "<one of six corruption types applied to the chosen text>"}

================================================================================
PHASE 5: TRAINING -- 5-RUN ABLATION GRID
================================================================================

1. CONFIG (config.yaml -- the single source of truth for every hyperparameter,
   no per-run hardcoding):

   peft:
     lora_r: 8
     lora_alpha: 16
     lora_dropout: 0.05
     target_modules: [q_proj, k_proj, v_proj, o_proj]
     qlora_4bit: {load_in_4bit: true, bnb_4bit_quant_type: nf4, bnb_4bit_compute_dtype: bfloat16}
   training:
     max_seq_length: 1024        # right-sized by directly tokenizing every
                                  # real prompt+target across all splits --
                                  # true max was 983 tokens; the original
                                  # 2048 default was never once being used.
     sft:  {epochs: 3, per_device_batch_size: 2, gradient_accumulation_steps: 8, learning_rate: 2.0e-4}
     dpo:  {epochs: 1, per_device_batch_size: 2, gradient_accumulation_steps: 4, learning_rate: 5.0e-5, beta: 0.1}

2. THE 5 RUNS (each driven by ONE parameterized script via CLI flags --
   --load-in-4bit / --adapter present or absent -- not per-run copies):

   | run_id         | script          | method | precision      | warm start           |
   |----------------|-----------------|--------|-----------------|-----------------------|
   | baseline       | (no training)   | none   | zero-shot       | --                    |
   | sft_qlora      | train_sft.py    | SFT    | 4-bit QLoRA     | --                    |
   | sft_lora_fp    | train_sft.py    | SFT    | full bf16       | --                    |
   | dpo_from_base  | train_dpo.py    | DPO    | 4-bit QLoRA     | none (fresh LoRA)     |
   | dpo_from_sft   | train_dpo.py    | DPO    | 4-bit QLoRA     | sft_qlora adapter     |

   - trl.SFTTrainer, prompt/completion format (automatic completion-only
     loss masking).
   - trl.DPOTrainer; warm start continues the SAME LoRA weights via
     PeftModel.from_pretrained(..., is_trainable=True) rather than merging
     first (not straightforward on a 4-bit-quantized base). DPOTrainer
     uses the model itself, with adapters disabled, as its own implicit
     reference model when it's already a PeftModel -- avoids a second full
     model copy in memory.

3. THE 9-STEP DEBUGGING CHAIN THAT MADE REAL TRAINING RUNS WORK (condensed
   here; full detail in LOG.md and WRITEUP.md Section 4.2):
   1. Raw-transformers teacher generation: 4 bugs (padding, device split,
      unbounded generation length, OOM) -> abandoned for Ollama (Phase 3).
   2. Local SFT smoke test caught a SILENT loss-masking bug: with no
      separator between prompt and completion, BPE merged the boundary
      into the masked side -- every example was silently never trained to
      predict its own first token. Fixed at the template source
      (CANONICAL_PROMPT_TEMPLATE), then regenerated `prompt` fields
      everywhere.
   3. First real Kaggle SFT run: OOM (gradient_checkpointing never set).
   4. Second attempt: 12h timeout at ~230s/step -- device_map="auto" split
      the model across a T4x2 session (same bug class as step 1, new file).
   5. Third attempt: still ~117-125s/step even pinned correctly -> adopted
      Unsloth as an opt-in accelerated path (kept alongside the vanilla
      path, since Unsloth couldn't be validated on the local dev machine).
   6. First Unsloth run: crashed on a bf16/Ampere+ validation check --
      revealed the ACTUAL root cause of the mystery slowness all along:
      T4/Turing lacks Tensor Core bf16 acceleration. Fixed by computing GPU
      compute-capability at runtime, bf16 only on Ampere+, fp16 otherwise.
   7. Result: sft_qlora trained end-to-end at a stable ~7-8s/step (~2.3-2.5h
      total, 1,125 steps).
   8. sft_lora_fp (full-precision ablation) trained cleanly but eval
      crashed on a peft/torchao version incompatibility unique to loading a
      LoRA adapter onto a full-precision (not 4-bit) base. Adapter was
      already saved to disk -- recovered with a minimal eval-only notebook
      instead of re-training.
   9. Two silent-wrong-adapter bugs caught before they mattered: a Kaggle
      adapter auto-discovery helper returned the FIRST directory matching a
      content marker -- with dry-run/checkpoint artifacts also present,
      unordered directory traversal could silently select an
      under-trained adapter with NO error. Fixed to require exactly one
      match after filtering dry-run/checkpoint paths, erroring loudly on
      ambiguity.

4. ADAPTER OUTPUT: adapters/{sft_qlora, sft_lora_fp, dpo_from_base,
   dpo_from_sft}/ -- final-state LoRA weights only (checkpoints cleaned up).

================================================================================
PHASE 6: EVALUATION -- DUAL METRIC, NOT ONE SCORE
================================================================================

1. WHY TWO METRICS: each has a real, different blind spot. A rubric alone
   is mechanical (misses genuine legal-reasoning errors with no lexical
   overlap to flag them); an LLM judge alone can be fooled by fluent,
   well-structured, hallucinated prose. Neither dominates the other -- see
   finding below.

2. DETERMINISTIC RUBRIC (src/eval/rubric.py) -- 4 components, reported
   SEPARATELY, never blended into one hiding number:
   - structure_ok: all 4 IRAC sections present, in order, non-empty.
   - groundedness (most important): quoted spans in Application must be
     real substrings of the source clause (falls back to word-overlap for
     paraphrases -- a documented, known limitation); Rule must not invent
     legal authority (named courts/statutes/"held that"). Combined via
     min() -- either failing sinks the score.
   - length_ok: graded, catches truncation/rambling.
   - no_contradiction: heuristic term-pair contradiction check plus
     explicit self-reversal / self-hedging checks.
   - Needed 6 real bug fixes, all "too broad" heuristics matching a
     technically-true keyword in the wrong context (e.g. flagging
     "condition precedent," a standard contract term of art, as invented
     case-law "precedent"). Final: 35+ unit tests, full-dataset aggregate
     0.9874.

3. LLM-AS-JUDGE (src/eval/llm_judge.py):
   - Same qwen2.5:7b-instruct-q4_0 via Ollama.
   - 3 dimensions, 1-5 each (groundedness, reasoning_quality, overall) --
     not a single number, specifically to surface
     well-grounded-but-poorly-reasoned vs. well-reasoned-but-ungrounded.
   - Judged a seeded common 150-id subsample shared across all 5 runs (750
     calls total), not the full 803x5 -- a deliberate cost/signal tradeoff.
   - src/eval/sample_judge_ids.py picks the seeded subsample.

4. MANUAL VALIDATION OF THE JUDGE ITSELF
   (src/eval/sample_judge_validation.py):
   - 35-row stratified sample (15 lowest-judge-score, 10 largest
     rubric/judge disagreements, 10 random).
   - Reviewed via an external AI tool, explicitly self-labeled as
     model-generated triage, NOT human ground truth -- treated as such
     throughout (do not cite as inter-rater agreement).
   - 3 of its most consequential claims independently re-verified against
     raw clause/response text before being trusted (see Results below).

5. SCORE / CONSOLIDATION (src/eval/score.py,
   results/consolidated_summary.csv): merges rubric summary and judge
   summary side by side per run_id for the final comparison table.

================================================================================
PHASE 7: RESULTS -- WHAT THE ABLATION GRID ACTUALLY SHOWED
================================================================================

Rubric (full 803-row test set, 0-1 scale):

  run_id          structure_ok  groundedness  length_ok  no_contradiction  aggregate
  baseline         0.994         0.731         0.994      0.991             0.927
  sft_qlora        1.000         0.951         1.000      1.000             0.988
  sft_lora_fp      1.000         0.947         1.000      0.995             0.986
  dpo_from_base    1.000         0.976         1.000      1.000             0.994
  dpo_from_sft     1.000         0.985         1.000      1.000             0.996  <- best

LLM judge (150-row common subsample, 1-5 scale):

  run_id          groundedness  reasoning_quality  overall
  baseline         4.63          4.64               4.63
  sft_qlora        4.79          4.81               4.79
  sft_lora_fp      4.77          4.79               4.76
  dpo_from_sft     4.81          4.80               4.79
  dpo_from_base    4.83          4.84               4.82

KEY FINDINGS:
1. SFT closes the groundedness gap, and it dominates. Format compliance
   was never the real gap (structure_ok 0.994 even zero-shot);
   groundedness jumped 0.731 -> 0.951 after SFT alone (+0.220 absolute,
   the single largest move in the grid).
2. DPO improves further on the SAME dimension: dpo_from_sft moves
   groundedness another +0.034 (0.951 -> 0.985).
3. DPO alone gets surprisingly close to the full pipeline WITHOUT ever
   going through SFT: dpo_from_base (0.994 aggregate) came within 0.002 of
   dpo_from_sft (0.996), and clearly beat sft_qlora alone. Plausible
   mechanism: the chosen side of every DPO pair IS the same clean teacher
   target SFT trains on, plus DPO gets an explicit contrastive signal SFT
   never sees. The project's own original config had assumed
   DPO-needs-SFT-first as the default -- this ablation disproved that
   default assumption.
4. QLoRA's 4-bit quantization cost nothing measurable (sft_qlora
   marginally OUTSCORED sft_lora_fp full-precision) -- gap small enough to
   be single-run noise, honest claim is "quantization was free here."
5. The two metrics agree on DIRECTION but diverge sharply on MAGNITUDE --
   itself a real finding, investigated rather than hand-waved (see below).

WHY THE METRICS DIVERGE (a real, verified LLM-judge reliability problem):
A 35-row manual validation of the judge's own scores surfaced a
groundedness blind spot, independently re-verified against source text:
  - Judge scored a response groundedness 5/5, wrote "there are no invented
    facts" -- while the response fabricated an entity name ("Mergers and
    Acquisitions (MLG)") out of the clause's actual party ("LMG").
  - Judge scored 4/5, faulting only imprecision -- while the response
    invented a carve-out contradicting the clause's own "under no
    circumstances" language.
  - Judge penalized a response for "not fully capturing" a requirement the
    response had actually named, twice.
Implication: the LLM judge's groundedness scores should not be taken at
face value on this task. The rubric, despite its own false-positive risk
on legitimate paraphrases, checks something mechanical (quote/word-overlap
against the real clause) that fluent prose alone can't satisfy. Neither
metric dominates -- the judge catches reasoning-level errors the rubric
structurally cannot see; the rubric is more reliable on fabrication
detection specifically. Reported as a finding, not smoothed over.

================================================================================
PHASE 8: SERVING -- LOCAL FASTAPI, NOT A CLOUD DEPLOY
================================================================================

1. WHY LOCAL: 4-bit inference of a 3B model fits the local 4GB GPU
   (unlike training, which never did) -- the one piece of this project
   deliberately NOT run on Kaggle.

2. src/serving/app.py:
   - Lifespan-based model load: base model + BitsAndBytesConfig(4-bit NF4)
     + device_map={"":0}, then PeftModel.from_pretrained(model, adapter_path)
     to attach the chosen adapter.
   - ADAPTER_NAME env var selects which of the 4 trained adapters to serve
     (defaults to dpo_from_sft, the best result on both metrics); unset it
     entirely for a zero-shot baseline comparison.
   - Reuses CANONICAL_PROMPT_TEMPLATE, parse_irac(), and
     is_substantive_clause() from src/data/build_irac.py -- the same
     single source of truth every training/eval stage already imports;
     never redefined inline.
   - Routes:
     GET  /health  -> {status, model_id, adapter_name, cuda_available}
     POST /analyze -> {category, clause_text} -> {issue, rule, application,
                       conclusion, parse_ok, raw_response, model_id,
                       adapter_name}; 422 if clause_text isn't substantive
                       (same filter used to clean the training data itself).

   Run: uvicorn src.serving.app:app --host 0.0.0.0 --port 8000

3. REAL ISSUES HIT STANDING THIS UP LOCALLY (first-ever local pull of the
   full 3B weights -- everything before this always ran on Kaggle):
   - Looked stuck at "Fetching 2 files: 0%" for 7+ minutes -- false alarm;
     Windows was writing the real ~6GB safetensors files directly under
     snapshots/ instead of the usual blobs/+symlink layout (a Windows
     symlink limitation), so the blobs/ folder looked empty even though
     the download had actually completed.
   - accelerate/bitsandbytes were listed in requirements.txt but never
     actually pip-installed locally (everything real ran on Kaggle where
     they came pre-installed) -- installing them locally is what triggered
     the torch CPU-wheel regression described in Phase 1.
   - Fixed, verified end-to-end: /health returns 200, /analyze returns a
     well-formed IRAC response on a real clause, and correctly 422s on a
     non-substantive fragment.
